# pygame-rs 分发形态设计稿：可执行文件 + 链接库双形态

> 状态：初步分析（2026-10-25，批次 60 前置设计）。
> 原则：**一核多壳**——核心逻辑（rpy 库 + testhost）不动，分发形态
> 只是不同的入口壳。本文只做分析与定约，不含实施代码。

---

## 1. 目标：两种形态各自服务谁

| | 可执行形态（exe） | 链接库形态（dll / so / dylib） |
|---|---|---|
| **用户** | 游戏玩家（双击即玩）、Python 游戏开发者 | 引擎集成者 / 工具链作者（C++ 启动器、编辑器、服务器、测试框架） |
| **宿主** | 操作系统（进程入口） | 宿主程序（dlopen/LoadLibrary 后调用） |
| **主循环归属** | pygame-rs 自己 | 取决于协议层级（见 §4） |
| **现状** | ✅ 已有（pygame-runner） | 部分（Android so = 系统 NativeActivity 驱动；Web wasm = JS 宿主驱动——两者本质已是链接库，只是入口协议不通用） |

**核心判断**：我们不是"要不要做链接库"，而是**把已有的两种隐式链接库形态
（Android/Web）与桌面统一到一个显式 C-ABI 协议上**——三平台一种嵌入语法。

---

## 2. 现状矩阵（盘点）

| 平台 | 产物 | 入口 | 驱动者 | 形态归类 |
|---|---|---|---|---|
| Windows | pygame-runner.exe | `main()`（bin） | 自持主循环 | 可执行 ✅ |
| Windows | examples\<名>.exe | `main()`（bin） | 自持 | 可执行（开发用） |
| Android | lib<名>_android.so | `android_main`（app_entry! 宏） | 系统 NativeActivity | 链接库（平台专有协议） |
| Web | <名>_bg.wasm | wasm-bindgen 导出（glue init()） | JS 胶水 | 链接库（JS 协议） |

已具备的地基：
- **核心是 rlib**（lib 面无 crate-type 定制）——壳们静态链接核心，一核多壳成立；
- **app_entry! 宏**已按平台分发生成入口（桌面 fn main / Android
  android_main / Web bin 存根）——壳的生成机制已有惯例；
- **starfish-render 的 raw-handle 族**（`RenderEntry::
  surface_from_raw_handles`）——宿主窗口/显示句柄建渲染表面的通道
  已通（宿主窗口嵌入的技术前提，绑定层尚未暴露）。

---

## 3. 核心原则：一核多壳

```
                ┌─ 壳A：bin pygame-runner ──→ exe（已有）
   rpy 库       │
 （testhost::run ├─ 壳B：example 壳 ───────→ exe（开发用，已有）
   + install）  │
                ├─ 壳C：C-ABI 导出壳 ──────→ dll / so / dylib（新增）
                │
                ├─ 壳D：android_main 壳 ──→ .so（已有；未来可重定向到 C-ABI）
                └─ 壳E：wasm-bindgen 壳 ──→ wasm（已有）
```

要点：
- 壳只做**入口翻译**（把各自平台的入口约定翻译成对核心的一次调用序列），
  不含业务逻辑；
- 壳 C（C-ABI）与壳 B/D/E 平级——新增它不触碰任何现有形态；
- 打包脚本（build_windows 等）对 exe 形态零变化；链接库形态走独立
  产物目录（dist/lib/）。

---

## 4. C-ABI 协议设计（壳 C 的核心）

两级粒度，按宿主需求选用：

### 4.1 一把梭级（宿主不管循环）——v1 先做

```c
// pygame_rs.h（cbindgen 生成或手写）
// 运行一个游戏目录（阻塞至游戏退出）；协议与 runner 完全一致：
// game_dir 内 game.toml [entry] → main.py → async def main()
int  pgrs_run(const char* game_dir);

// 同上，但脚本来自内存（宿主自有加载管线时）
int  pgrs_run_script(const char* script_utf8, const char* base_dir);

// 版本与能力查询（诊断用）
const char* pgrs_version(void);
```

- 语义 = 把 runner 的 `main()` 原样导出——**实现成本约一天**
  （#[no_mangle] extern "C" 包装 + cdylib crate-type）；
- 适用：自研启动器、CI 冒烟、脚本化测试。

### 4.2 宿主持循环级（宿主有自己的帧循环）——v2 按需

```c
int  pgrs_init(int width, int height, unsigned flags);  // 建窗/装配
int  pgrs_step(void);      // 推一帧（事件→Python 协程步进→上屏）；返回 0=继续 1=退出
void pgrs_shutdown(void);
```

- 难点不在导出而在**主循环拆分**：testhost 的 run() 是一体的
  async 块——step 化需要把"帧拍"（next_frame）的驱动权交给宿主调用
  节奏（本质 = 壳内一个 Future 状态机，step = poll 一次）；
- 与 §5 窗口归属形态 b 联动（编辑器嵌入场景）。

---

## 5. 窗口归属三形态（链接库形态的关键分叉）

| 形态 | 窗口来源 | 用途 | 地基 |
|---|---|---|---|
| a. 库自建窗 | pgrs 内部建（与 runner 同） | 启动器/工具，v1 | ✅ 现成 |
| b. 宿主窗口 | 宿主传 raw window/display handle | 编辑器嵌入、引擎内嵌 | ✅ starfish-render `surface_from_raw_handles` 已通，**绑定层待暴露** |
| c. 离屏无窗 | 渲染到纹理/共享内存回传 | 服务器渲染、视频生成、自动化测试 | 部分具备（Surface 离屏链路在；回传通道待做） |

v1 定约：只做形态 a；形态 b/c 各自立项（b 的引擎地基已在，量在绑定层
参数协议；c 需新增读回通路）。

---

## 6. ABI 稳定定约

- **v1 不承诺跨版本 ABI**：Rust cdylib 的符号布局随编译器/依赖版本
  变化——定约"**同一仓库同一提交编译的库与头文件配套分发**"；
- 头文件随构建产出（cbindgen 或手写 pygame_rs.h，量小建议手写——
  符号仅 3~4 个）；
- Android 现有 so 不受影响（NativeActivity 协议保持；未来若统一，
  android_main 壳内部改调 C-ABI step，对外行为不变）。

---

## 7. 构建与打包落点

- `Cargo.toml`：`[lib] crate-type = ["rlib", "cdylib"]`（rlib 保留
  ——examples/bin 仍静态链；cdylib 新增产 dll/so/dylib）；
- 产物命名：`pygame_rs.dll / libpygame_rs.so / libpygame_rs.dylib`；
  Android 不变（现有 `<名>_android` 惯例）；
- 打包脚本：`build_windows.py` 等**不接管**库形态（库的消费者是
  集成者，不是游戏分发链）；新增轻命令 `cargo build --release
  --lib` + 头文件拷贝即可（或并入未来 build_lib.py，量极小）；
- features：库按需编译（`--features gui` / `physics3d`）——库体积
  由集成者选择。

---

## 8. 脚本与资源协议（与 runner 完全一致）

链接库形态复用已定稿的入口三件套，零新概念：

```
game_dir/
  game.toml      # [app] entry = "main.py"
  main.py        # async def main(): ... await pygame.next_frame()
  assets/...
```

宿主只负责"给一个目录或一段脚本 + 一个基准目录"——加载、装配、
驱动全部在库内（与 runner 同一条 testhost::run 路径）。

---

## 9. 实施路径

| 阶段 | 内容 | 量级 |
|---|---|---|
| 1 | crate-type 加 cdylib + `pgrs_run/pgrs_run_script/pgrs_version` 导出 + 手写头文件 + 桌面 dll 宿主冒烟（一个 20 行 C 或 Python ctypes 测试程序） | ~1 天 |
| 2 | （按需）pgrs_init/step/shutdown 宿主持循环级 + Android 壳内统一 | 中 |
| 3 | （按需）窗口归属 b（raw-handle 绑定层暴露）与 c（离屏回传） | 中 |

---

## 10. 开放问题（实施前需定夺）

1. 壳 C 是否需要独立于 `gui` feature 的最小 feature 集（无渲染纯
   逻辑宿主？——建议不做，库的最小意义就是带渲染）；
2. `pgrs_run` 的窗口尺寸/标题等参数：v1 沿用 game.toml 扩展段
   （`[window] width/height/title`）还是加函数参数（倾向 toml——
   协议零参数最稳）；
3. Web wasm 是否补一份"无 JS 胶水假设"的说明文档（现有 glue 是
   事实协议，暂不动）。
