# pygame-rs 开发与游戏打包体系设计稿

> 状态：初步分析（2026-10-25，批次 61 前置设计；承接《分发形态双形态
> 设计稿》——那份管"库怎么被嵌入"，本文管"开发者怎么开发、游戏怎么
> 分发"）。仅设计，未动代码。
>
> 技术事实基础（已核实）：
> - RustPython marshal 完整（compiler-core `serialize_code` /
>   `deserialize_code` 现成）——**字节码分发可行**；
> - RustPython **内置 zipimporter**（vm import.rs `path_hooks` 已挂
>   zip 导入）——**zip 容器内 import 零自研起步**。

## 1. 总纲：开发与打包彻底分离

```
开发链（开发者日常）                      打包链（发布时）
─────────────────────                    ─────────────────────
pypg.exe（"pygame 的 python"）            build_windows / web / apk
  pypg my_game            ← 同一个引擎 →    dist/<名>/（exe+wasm+apk）
  pypg -c "print(1)"
  pypg script.py（任意脚本）
        │                                      │
        └──────── games/<名>/ 开发态 ──────────┘
             main.py + assets（纯目录，三平台
             io 直读——"打包脚本控制资源"定约）
```

分离定约：
- **pypg = 开发解释器**（"导出的 python 可执行文件"）：pygame 全量
  内置、无需 Rust 工具链；即 pygame-runner 的开发态定位升级（更名
  + 三种调用形态：REPL / `-c` 单行 / 脚本直跑；游戏门形态
  `pypg --game dir` 走 async main 协议）；
- **build_\*.py = 分发打包器**：只负责把 games/<名>/ 变成各平台
  分发单元——开发态与发布态互不感知。

## 2. 游戏包格式 .pgz（解决"脚本/资源打包加密"）

### 2.1 容器 = zip（三平台通吃，解压工具遍地）

```
my_game.pgz（zip 容器）
  manifest.toml        # entry / 平台项 / 打包选项（见 2.4）
  main.py              # 或 main.marshal（字节码形态，见 2.3）
  lib/my_mod.py        # 游戏自己的多文件模块（zipimport 直读）
  assets/**            # 资源
```

### 2.2 保护分级（开发者按需选择，打包参数一行决定）

| 级 | 形态 | 防护对象 | 成本 |
|---|---|---|---|
| L0 | 目录散装（现状） | 无 | — |
| L1 | .pgz 明文 zip | 单文件分发整洁 | ≈零（zip + zipimport 现成） |
| L2 | **字节码化**：.py → marshal（`serialize_code`） | 源码不可直接阅读（反编译门槛低，拦小白） | 低 |
| L3 | **AES 加密包体**：zip 条目整体加密 + 密钥派生内嵌分发单元 | 普通用户无法解包 | 中（见 2.5） |

定约：**不做**自定义 VM 变换级保护（L4）——维护成本失控，且对本项目
的受众（独立游戏）L3 已超配。

### 2.3 字节码化（L2）链路

```
打包脚本（Python 侧做不了——须在 Rust 侧）：
  build 时经 access 到 vm：compile(src) → marshal::serialize_code
  → 写入 main.marshal / lib/*.marshal
运行侧：
  runner 读 .marshal → deserialize_code → run_code_obj（跳过 compile）
```

- 附带收益：启动加速（免编译）+ 语法错误前置到打包期；
- 注意：marshal 版本与 RP 绑定（同仓同版本——与 C-ABI 定约一致，
  manifest 记 `bytecode_ver`，不匹配回退 .py）。

### 2.4 manifest.toml（包内清单）

```toml
[app]
name = "my_game"
entry = "main"              # 模块名（不再是文件名——支持 lib/ 包）
bytecode = "marshal"        # "" | "marshal"（L2 标记）

[platforms]                 # 平台差异资源的声明位（见 §4）
web.import_map = "import_map.toml"   # 打包期生成的 import 清单

[encrypt]                   # L3 标记
scheme = "aes-256-gcm"
```

### 2.5 加密（L3）密钥模型

- 打包时 `--encrypt`：随机生成 256-bit key → AES-GCM 加密 zip 条目
  → key 派生材料写进**分发单元**（Windows: exe 尾部附加段；Web:
  wasm 旁 key.js；Android: APK assets）——运行时内存解密，不解落盘；
- 明确边界：**密钥随分发单元走** = 防君子不防逆向（业内通行）；
  追求更强保护 = 自定义壳方向，不在本项目范围。

## 3. 资源提供者抽象（io 层统一——三后端）

落地在 starfish-io（用户既有定约"跨平台 io + 打包脚本控制资源"的
自然延伸）：

```
资源路径统一前缀          后端
assets://foo.png    →   DirProvider(game_dir/assets)      （L0/L1 桌面/Android）
                    →   ZipProvider(pgz)                  （L1/L2）
                    →   EncZipProvider(pgz, key)          （L3）
                    →   FetchProvider(base_url)           （Web 明文）
```

- `open()/image.load/mixer` 资源入口全部走 provider 链（前缀路由）；
- 游戏代码零改动跨 L0→L3（同一 `assets://` 路径语义）；
- Web 加密（L3-web）：key 经 wasm 内嵌同 L3。

## 4. 平台间 import 一致性（深水区的核心）

### 4.1 差异源拆解（先分类再解决）

| 差异源 | 性质 | 对策 |
|---|---|---|
| RustPython vs CPython stdlib 子集 | **运行时能力**（无法"解决"，只能管理预期） | §4.4 兼容面清单 |
| 游戏自有模块 `import lib.foo` | **路径发现**——桌面 fs 列目录 / Web fetch 不能列目录 | §4.2 import 清单 |
| 平台特有模块（os/subprocess/权限） | **能力边界** | `pygame.platform` 查询面（§4.3） |
| sys.path 形态各平台不同 | 协议不一致 | §4.2 统一资源 URI |

### 4.2 方案：打包期 import 清单 + 运行期统一 finder

```
打包时（build_*.py 的 ast 扫描——纯 Python，打包脚本能力范围内）：
  遍历游戏 .py 的 import 语句 → 生成 import_map.toml
  （模块名 → pgz 内路径；含动态 import 的手工补录段）

运行时（pypg/runner 装配）：
  注入自定义 finder（RustPython 标准协议）：
    finder 只查 import_map（O(1)，不列目录）
    → 从 pgz/dir 读源码或 marshal → exec_module
  sys.path 全平台恒等：游戏根 + pgz 根（资源 URI 形态）
```

- zipimporter 兜底（容器内 .py 直读——内置能力）；
- **效果**：同一游戏代码三平台 import 行为完全一致（差异被清单+finder
  吸收在引擎内，开发者无感知）；
- 动态 import（importlib.import_module(变量名)）：打包期静态扫描不
  全覆盖 → manifest 手工补录段 + 未命中时的明确报错（指路补录），
  不做运行时全盘扫描（Web 列不了目录，物理不可能）。

### 4.3 平台能力查询面

`pygame.platform.current() -> "windows" | "android" | "web"` +
`pygame.platform.has("clipboard")` 式能力位——替代裸 `sys.platform`
猜测惯用法（文档推荐唯一正道）。

### 4.4 兼容面管理（RustPython stdlib 子集）

- 定约：**不承诺 CPython 全量**；维护"已验证模块清单"（文档页，
  随批次生长——绑定层已有 46 项自测即雏形）；
- 游戏 import 未实现模块 → 打包期清单生成时**即警告**（提前暴露，
  而不是运行到目标平台才炸）。

## 5. 打包命令形态（开发者视角终态）

```
python scripts/pack.py games/my_game            # 生成 .pgz（L1/L2/L3 参数）
python scripts/build_windows.py games/my_game   # pgz + exe → dist/（现状链路吸收）
python scripts/build_web.py games/my_game       # 通用 wasm runner + pgz（立项中）
python scripts/build_apk.py games/my_game       # 通用 so + assets/pgz（立项中）
```

pack.py 与 build_* 的关系：pack 产 .pgz（内容层），build 产分发单元
（形态层）——build 的 games/ 目录输入兼容散装与 pgz 两种。

## 6. 实施路径（依赖排序）

| 阶段 | 内容 | 依赖 | 量级 |
|---|---|---|---|
| P1 | pypg 开发解释器三形态（REPL/-c/脚本 + --game 门） | runner 现成 | 小 |
| P2 | .pgz L1（zip + manifest + zipimport 验证） | §2.1 | 小 |
| P3 | import 清单 + 统一 finder（三平台 import 一致性） | P2 | 中 |
| P4 | L2 字节码化（marshal 链路 + 打包期编译） | P2 | 小 |
| P5 | 资源 provider 抽象（assets:// 三后端） | P2 | 中 |
| P6 | L3 AES 加密链 | P4/P5 | 中 |
| P7 | 通用 Web/Android runner（吸收 pgz 输入） | 已立项 | 中 |

P1–P4 即可交付"开发者打包三平台一致 + 源码不裸奔"的最小完整闭环。

## 7. 开放问题（实施前定夺）

1. pypg 是否要 venv/pip 形态（装第三方纯 Python 包）——建议 v1 不做
  （RustPython pip 生态残缺，文档明示"pygame 全内置"边界）；
2. .pgz 是否多游戏一包（合集形态）——manifest 支持数组即可，按需；
3. import 清单的动态 import 报错严格度：警告放行 vs 打包失败
  （倾向：打包警告 + 运行未命中清晰报错）。
