# 方案 A 到底怎么工作：用大白话重讲一遍

我用一个具体场景，从"开发者写什么"到"代码怎么跑起来"，一步步走。

---

## 场景设定

- **开发者**写了一个文件 `game.py`，里面写了 `import mymod`。
- **你**（引擎作者）要把这个 `game.py` 跑起来，`mymod` 也要能 import 到。

---

## 第一步：理解"import 时发生了什么"

当 Python 执行 `import mymod` 时，RustPython 的导入系统会**按顺序问几个"查找器"**：

```
import mymod
   │
   ▼
问 sys.meta_path 里的第一个 Finder："你知道 mymod 在哪吗？"
   │  回答 None（不知道）
   ▼
问第二个 Finder："你知道 mymod 在哪吗？"
   │  回答 None
   ▼
... 一直问到原生 PathFinder（读磁盘的）
   │  回答"在 /path/to/mymod.py"
   ▼
读文件、编译、执行，mymod 进 sys.modules
```

**`sys.meta_path` 就是"查找器列表"**。谁先回答"我知道"，就用谁。

---

## 第二步：方案 A 做的事——往列表最前面插一个你自己的 Finder

你（宿主）在启动时，**往 `sys.meta_path` 最前面插一个 Finder**：

```python
# 这段是你（宿主）注入的，开发者看不到
class SfFinder:
    def find_spec(self, fullname, path, target=None):
        src = sf_read_module_source(fullname)   # ← 调你 Rust 侧的函数
        if src is None:
            return None                          # 我不知道，问下一个
        return 一个"我知道怎么加载"的 spec

sys.meta_path.insert(0, SfFinder())
```

**从此，每次 `import xxx` 都先问 `SfFinder`。**

---

## 第三步：`sf_read_module_source` 是什么——你 Rust 侧写的函数

这是你在 Rust 里暴露给 Python 的一个函数：

```rust
#[pyfunction]
fn sf_read_module_source(name: &str) -> Option<Vec<u8>> {
    // 开发者环境：读磁盘文件
    // 打包后：从资源包/嵌入数据读
    // 找不到：返回 None
}
```

**它是"按模块名取源码字节"的唯一入口。** 不同环境，内部实现不同：

| 环境 | `sf_read_module_source("mymod")` 内部做什么 |
|------|------------------------------------------|
| 开发者（桌面） | 在 `sys.path` 里找 `mymod.py`，读文件返回字节 |
| 打包（Web/移动） | 从 zip / 嵌入资源 / 网络按名字取字节 |
| 找不到 | 返回 `None`（让下一个 Finder 接手） |

---

## 第四步：完整流程走一遍

**开发者写 `game.py`：**
```python
import mymod
mymod.do_something()
```

**你启动引擎时：**
```rust
// testhost::run 里
rpy::install_pygame(vm);           // 注入 pygame
rpy::install_module_finder(vm);    // ← 新增：注入 SfFinder 到 sys.meta_path
// 然后 compile + run game.py
```

`install_module_finder` 内部做的事（伪代码）：
```rust
// 往 sys.meta_path 插一个 Finder，Finder 的 find_spec 调 sf_read_module_source
let sys = vm.sys_module.get_attr("meta_path", vm)?;
sys.insert(0, 构造好的 SfFinder 对象, vm)?;
```

**执行 `game.py` 时：**
```
执行 import mymod
   │
   ▼
问 sys.meta_path[0] = SfFinder："mymod 在哪？"
   │
   ▼
SfFinder.find_spec 调 sf_read_module_source("mymod")
   │
   ├─ 开发者环境：读到 /path/to/mymod.py 的字节 → 返回字节
   ├─ 打包环境：从资源包读到字节 → 返回字节
   └─ 找不到：返回 None → 问下一个 Finder
   │
   ▼
SfFinder 拿到字节，告诉导入系统："我知道怎么加载，用这个字节"
   │
   ▼
RustPython 编译字节、执行、mymod 进 sys.modules
```

---

## 第五步：开发者要做什么？

**什么都不用做。** 他写 `import mymod`，和普通 Python 一模一样。

Finder 是你注入的，`sf_read_module_source` 是你写的。**开发者感知不到 Finder 的存在。**

---

## 第六步：为什么这是"行为一致"

| 环境 | `import mymod` 的结果 | 开发者写的代码 |
|------|---------------------|--------------|
| 开发者（桌面） | SfFinder 读磁盘文件 → 加载成功 | `import mymod` |
| 打包（Web/移动） | SfFinder 读资源包 → 加载成功 | `import mymod`（**一模一样**） |

**开发者写的 `import mymod` 在两个环境都能跑通。** 区别只在 `sf_read_module_source` 内部"从哪读"——这是**宿主的事**，不是开发者的事。

---

## 第七步：和"手动加载"的区别

你可能问："这不还是手动吗？"

| | 手动加载（你担心的） | 方案 A |
|--|-------------------|--------|
| 谁触发加载 | **你**在启动时遍历所有文件，主动 import | **开发者脚本里的 `import` 语句**触发 |
| 什么时候加载 | 启动时一次性全加载 | **用到才加载**（惰性） |
| 加载哪些 | 所有文件 | **只加载被 import 的** |
| 开发者写什么 | 不变 | 不变 |

**方案 A 不是"你手动加载所有模块"，而是"你提供加载入口，开发者 `import` 时自动触发"。** 惰性、按需，不吃的内存只随实际 import 增长。

---

## 第八步：一张图总结

```
开发者写：game.py 里 import mymod
                │
                ▼
你启动时注入：sys.meta_path.insert(0, SfFinder)
                │
                ▼
执行 import mymod
                │
                ▼
SfFinder.find_spec("mymod")
    └─ 调 sf_read_module_source("mymod")   ← 你 Rust 侧写的
         ├─ 桌面：读 mymod.py 文件
         ├─ 打包：读资源包
         └─ 找不到：返回 None
                │
                ▼
拿到字节 → RustPython 编译执行 → mymod 可用
```

---

## 一句话回答

> **方案 A = 你在启动时往 `sys.meta_path` 插一个 Finder，Finder 的 `find_spec` 调你 Rust 侧写的 `sf_read_module_source(name)` 按需取源码字节。开发者只写普通 `import mymod`，触发 Finder，Finder 从"桌面读文件 / 打包读资源"取字节交给 RustPython 加载。开发者零感知，加载是惰性的（用到才读），不是启动时全量加载。**
